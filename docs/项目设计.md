# 项目设计：源码分层 + 打包成 Shopify 主题

面向**复杂 Liquid 主题**的常见工程做法：源码可按业务域分子目录，构建后再变成 Shopify 要求的扁平主题目录。

---

## 为什么要这样？

Shopify 运行时 / `theme push` **只认扁平结构**（`sections/`、`snippets/`、`assets/` 等不能随意嵌套）。  
所以行业做法是：

```
源码（你怎么舒服怎么分）  →  构建/打包  →  符合 Shopify 的产物目录
```

本仓库产物目录是 **`theme/`**（也有人叫 `dist/`）。

---

## 示意结构（通用形态）

```
src/                          # 源码（可分层）
  components/product-card/    # liquid + css + js 可放一起
  sections/home/
  sections/pdp/
  styles/
  scripts/
dist/                         # 或根目录 theme/ —— 扁平产物，给 CLI push
```

本仓库实际约定见 [开发流程.md](./开发流程.md) 与根目录 [README.md](../README.md)：

- 自定义区块：`src/sections/<域>/<name>/`
- 前端入口：`src/entrypoints/`
- 扁平产物：`theme/`（含 Dawn 底稿 + 构建结果）

---

## 构建常见栈

| 方案 | 说明 |
|------|------|
| **Vite + `vite-plugin-shopify`（Barrel）** | 代理商里很常见；管 JS/CSS 打包、`vite-tag`、开发 HMR（本项目已用） |
| **Webpack / 自定义脚本** | 把 component 拷平到 `sections/`、`snippets/`，JS/CSS 打进 `assets/`（本项目的 `build-liquid` 属这类） |
| **源码侧预处理** | Design token、SCSS/PostCSS、TypeScript 等都在源码侧处理，再输出到主题 |

本项目分工：

- **Liquid 扁平化** → `scripts/build-liquid.mjs`
- **JS/CSS** → Vite + `vite-plugin-shopify`

---

## 优点

- 能组件化（liquid / css / js 按功能聚在一起）
- 能管依赖、能测试
- 多人可按业务域拆目录协作

## 代价

- 要维护构建流水线
- 要维护路径映射（源码路径 → 扁平文件名）
- 主题编辑器改 `templates/*.json`、`settings_data.json` 时，要有冲突合并策略

---

## 和更大公司方案的关系

| 层级 | 做法 |
|------|------|
| 本层 | 自己分目录，再打包给 Shopify（复杂 Liquid 主题的正经做法） |
| 再往上 | 把复杂度挪到 **Theme App Extension**、**Checkout UI Extension**，或直接 **Headless（Hydrogen 等）**，而不是只在主题里堆文件夹 |

**一句话：** 可以自己分目录再打包给 Shopify，这是复杂 Liquid 主题的正经做法；更大的公司会进一步把复杂度挪到 App Extension 或 Headless，而不是只在主题里玩文件夹。
